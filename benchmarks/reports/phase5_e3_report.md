# 阶段五 E3 报告：跨模块同符号碰撞与语义改写消歧

> 生成时间：2026-11-13
> 数据集：`benchmarks/data/phase5_e3_collision_disambiguation.json`（20 题）
> 评测脚本：`benchmarks/eval_phase5_e3.py`
> 向量模型：`fastembed-BAAI/bge-small-zh-v1.5`（dim=512）
> 机器可读结果：`benchmarks/results/phase5_e3_metrics.json`

---

## 一、这个实验要反驳什么

阶段四的 `phase4_hard_negatives_report.md` 里有一组让评审直接怀疑产品价值的数字：

| 通道 | Top-1 |
| :--- | ---: |
| 单向量 | 60.00% |
| **单 FTS5** | **100.00%** |
| 混合融合 | 100.00% |

**融合相对纯 FTS5 的净增益是 `+0.00pp`。** 挑剔的读者会立刻问：既然纯 FTS5 已经 100%，为什么要背一个向量库？

根因不在融合算法，在**阶段四的题目本身**：20 道题把唯一定位符号（如 `ERR_XA_PROTO_08`）直接写进了 query，于是整个任务退化成纯词法匹配，向量通道根本不需要发挥作用，融合自然也无从增益。

E3 的设计目标就是构造一个**两个单通道都不可能单独完成**的任务，把差距真正拉开。

---

## 二、实验设计

### 2.1 跨模块同符号碰撞

* **模块 A**：分布式账务清算服务，部署 `v2.14.37 / v2.14.38 / v2.14.39`
* **模块 B**：边缘网关流控中间件，**同样部署** `v2.14.37 / v2.14.38 / v2.14.39`

同一版本号在 A、B 两个模块下**取值不同**，因此正确答案唯一，但符号本身完全重叠。

### 2.2 语义改写 Query

```
当支付对账系统升级到 v2.14.38 时，超时参数应配置为多少？
```

「支付对账系统」与原文「分布式账务清算」**零字面重叠**。

### 2.3 为了防作弊做的四件事（这决定数据可不可信）

这一版数据集在构造时主动消除了四类会制造假象的捷径：

| 防护项 | 做法 | 为什么必须 |
| :--- | :--- | :--- |
| 记忆正文不含模块正名 | 正文里只出现 `settle_timeout_ms` / `upstream_timeout_ms` 这类参数键，绝不写「分布式账务清算服务」 | 否则向量与 FTS 都能靠**字面重合**蒙对模块，把巧合当成消歧能力 |
| 改写词不出现在正文 | 「支付对账系统」等改写词不进入任何记忆正文 | 否则 query 与正文共享字面即等于直接命中 |
| 记忆 ID 中性化 | 统一编号 `M01..M06`，不含模块字母 | FTS 在 A/B 同版本平局时会回退到 memory_id 字典序；若 A 侧恒为小 ID，A2 会被系统性抬到假性 100% |
| 目标侧与 ID 极性正交 | 目标模块 A/B 各 10 题；「A 拿小 ID」与「B 拿小 ID」各 10 题，两个维度正交 | 保证平局兜底对两侧是**对称**的（实测 `target_is_lex_min_in_tie = 10/20 = 0.50`，正好抛硬币） |

数据集自带 `audit` 字段记录上述自检结果，可复核。

## 四、为什么融合能赢：两个通道各自的盲区

### 4.1 逐题拆解 A1 与 A2 的成功集合

| 类别 | 题数 |
| :--- | ---: |
| 仅 A1 答对 | 5 |
| 仅 A2 答对 | 5 |
| A1、A2 都答对 | 5 |
| A1、A2 都答错 | 5 |
| **至少一个单通道答对（并集）** | **15 / 20 = 75%** |

两个单通道的成功案例**高度互补**（各独占 5 题）。它们分别锁定任务的两个不同维度，没有任何一个通道覆盖全部 20 题。

融合拿到 **18/20 = 90%**，不仅吃下了并集的 15 题，还在 **A1、A2、A3 三个单通道全部答错的 5 题里额外救回 4 题**
（`E3_03`、`E3_06`、`E3_07`、`E3_15`，仅 `E3_11` 未救回）——这是融合产生的、单通道不具备的新信息。

### 4.3 维度判别率：把"各锁一个维度"量化

| 通道 | 模块判别正确 | 版本判别正确 |
| :--- | ---: | ---: |
| A1 纯向量 | **18 / 20 = 90%** | 11 / 20 = 55% |
| A2 纯 FTS5 | 10 / 20 = 50% | **20 / 20 = 100%** |
| A4 混合融合 | **18 / 20 = 90%** | **20 / 20 = 100%** |

这张表是本节最硬的证据：

* A1 模块对 90%、版本只对 55% → **强于模块，弱于版本**
* A2 版本对 100%、模块只对 50%（且这 50% 全是平局抛硬币）→ **强于版本，无模块能力**
* A4 两个维度同时达到各自的上限 → **融合真正把两个通道的能力并了起来**

另外实测 A3 纯槽位的 4 次命中**全部落在 A1∪A2 的并集之内**，没有贡献任何独占正确。

### 4.4 必须主动披露：A3 是一条退化基线

独立复核发现，在本题集上 A3 并不是一个"真实机制"，而是一个**常量预测器**：

* 20 题里 `slot_hit` **全部为 0**——因为 query 一律用旁称指代模块，`subject`/`predicate`
  的原文从不出现在 query 中；
* 于是 A3 的排序在 20 题里**恒为 M01 排第一**；
* 而正确答案恰好落在 M01 的比例是 4/20 = 20%；
* **A3 实测 4/20 = 20%，与"恒答 M01"这条最朴素基线完全一致。**

也就是说，槽位机制在本实验中的贡献是 **0**，A3 的 20% 不代表任何能力。

我们保留这一行而不是把它删掉，原因是：删掉它会让表格看起来只剩"我们赢了的对比"。
诚实的读法是——**这张表是两条真实基线（A1、A2）加一条退化基线（A3）**，
而不是三条真实基线。这一点同时写进了 README。

### 4.2 平局侥幸剥离：这是本报告最重要的一张表

| 通道 | Top-1 命中 | 其中纯靠 memory_id 字典序平局获胜 | **真实能力命中** |
| :--- | ---: | ---: | ---: |
| A1 纯向量 | 10 | 0 | **10** |
| **A2 纯 FTS5** | 10 | **10** | **0** |
| A3 纯槽位 | 4 | 4 | **0** |
| **A4 混合融合** | 18 | **0** | **18** |

结论非常直接：

* **A2 的 50% 全体制来自平局抛硬币。** FTS5 能精确锁定 `v2.14.38` 这个版本号，但 A、B 两个模块的 `v2.14.38` 记忆在 BM25 上得到**完全相同**的分数，通道本身没有任何模块判别信息，最终只能靠排序回退规则二选一。它的 50% 就是一枚硬币。
* **融合的 90% 里没有一次平局侥幸**，全部来自两个通道分数真正叠加后的区分度。

换句话说：**A2 的 50% 与 A4 的 90% 不是同一个意义上的 50%**。只看裸命中率会把这两种性质完全不同的能力混为一谈。

---

## 4.5 90% 的机制分解

把融合的 90% 拆开看，它来自两个各自独立的环节：

```
① FTS 把正确版本锁进最高分并列集合 : 20/20 = 100%
② 在该版本的跨模块孪生对中，向量选中正确模块 : 18/20 = 90%
① ∧ ② = 融合 Top-1 命中 : 18/20 = 90%
```

**融合的全部增益来自"用 FTS 把候选从 6 条砍到 2 条"**——把一个 1/6 的选择题
变成 1/2 的选择题，再由向量在这 2 条里做语义判断。这也直接解释了天花板为什么是 90%
而不是 100%：它被向量的模块判别力（90%）锁死，与融合公式无关。

同时这也给出了一个可被检验的负面结论：**单纯把 FTS 权重调大并不会更好。**
实测 `alpha ∈ [0.2, 0.9]` 时融合恒为 90%，而 `alpha = 0` 或 `1.0` 时都掉回 50%。
说明 90% 不是调参调出来的，而是两个通道真正互补的结果。

## 五、诚实声明：哪里没达到预期

| 指标 | 蓝图预期 | 实测 | 差异 |
| :--- | ---: | ---: | :--- |
| A1 纯向量 | ≈ 33% | **50.00%** | **高于预期 17pp** |
| A2 纯 FTS5 | ≈ 50% | **50.00%** | 符合预期 |
| A4 混合融合 | 100% | **90.00%** | **低 10pp** |
| 净增益 | ≥ +50pp | **+40.00pp** | **低 10pp** |

**没有达到蓝图的 100% / +50pp。以下是不加修饰的原因。**

### 5.1 A1 为什么高于预期的 33%

蓝图假设向量在密集微差版本号面前发生「向量空间坍缩」，只能靠模块信息碰运气（≈1/3）。
实测：bge-small-zh-v1.5 对版本号的判别并非完全无能力——

* 模块判别正确率：**18/20 = 90%**（语义改写确实桥到了正确模块）
* 版本判别正确率：**11/20 = 55%**

所以 A1 = 90% × 55% ≈ 50%。版本号在向量空间里**有微弱但非零**的信号，不是完全坍缩。蓝图低估了这一点。

### 5.2 融合剩下的 2 题为什么答错

两题分别是 `E3_05` 与 `E3_11`，失败模式完全一致：

| case | 期望 | 实际 Top-1 | 期望项 vec/fts/fusion | 实际 Top-1 vec/fts/fusion |
| :--- | :--- | :--- | :--- | :--- |
| E3_05 | M02 | M05 | 0.5310 / 0.1052 / 0.3607 | 0.5387 / 0.1052 / 0.3653 |
| E3_11 | M05 | M02 | 0.5672 / 0.1052 / 0.3824 | 0.5696 / 0.1052 / 0.3839 |

**注意 `fts` 一列：两条命中记录的 FTS 分数完全相同（都是 0.1052）。** 这说明：

1. FTS 正确地锁定了版本号（两条都是 `v2.14.38`），但它对 A/B 两个模块**不提供任何判别信息**；
2. 此时融合的排序完全由向量那一点点模块分差决定，而这两题里向量恰好以 **0.002~0.003** 的微弱差距选错了模块；
3. 融合把这个误差按 `alpha=0.6` 传递下来，于是也错。

这是**机制边界的真实暴露**，不是数据瑕疵：当语义改写跨度较大、而向量在模块维度上只领先 0.003 时，融合无法凭空创造出它没有的信息。要让融合跨过这最后 10pp，需要的不再是调参，而是**更强的语义表示**（更大模型 / 领域微调），这已超出零依赖内核的范畴。

## 七、复现方式

```bash
# 向量模型走 HF 镜像（离线环境可预先缓存）
export HF_HOME=./.hf_cache
export FASTEMBED_CACHE_PATH=./.fastembed_cache

python benchmarks/eval_phase5_e3.py \
    --out benchmarks/results/phase5_e3_metrics.json

# 零依赖纯字面模式（无 fastembed 时的退化对照）
python benchmarks/eval_phase5_e3.py --provider builtin
```

随机性：本实验**无随机性**。embedding 确定性、BM25 确定性、平局按 memory_id 升序确定性兜底，重复运行逐字节一致。
