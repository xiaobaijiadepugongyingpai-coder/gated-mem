## 0. 一句话结论

`gated_mem.md` 的**工程骨架是对的**（事件溯源 + 槽位裁决 + 可撤销），但它建立在**四个已经过时或错误的前提**上：没人做过、连坐是护城河、没钱所以不能做实验，以及——最要命的一条——**持久化存储本身在它的目标基准上不产生增量价值**（StateMem 论文 Table 6：纯 prompt 改写 56.7–75.0 vs 完整系统 23.3–36.3）。

前三个前提如果不修正，7 天计划会把绝大部分工时投向已经被证明收益最薄的机制（连坐 −12.5pp、时效操作本身只值 2.0pp）。第四个前提如果不正面回应，**整个项目可能是在优化一个不存在的收益**。

但第四条同时也是机会：它精确定位了唯一可能赢的地方——**历史装不进上下文窗口的时候**。那是真实编码项目的常态，而论文明确承认持久化存储"在装不下时有用"，却没测。**那是一块没人占过的地。**

**我的建议**：
1. 把 `project_plan.md` 当作真正的方案，`gated_mem.md` 降级为技术设想集。
2. **先花 ¥0–50 跑第一刀**（322 probes，两条件，不含 ingest），拿到第一组数。
3. **第一刀里必须包含"纯 prompt 改写"这个对照臂**——否则你无法区分"方案有效"和"prompt 写得好"。
4. 在拿到这组数之前，不要写 Day 1 的代码。

## 1. 四个必须先修正的事实性前提

### 1.1 “全球开源界与学术界暂无 1:1 撞车”—— 不成立

`artifacts/competitive_landscape_analysis.md:5` 写的是“**全球开源界与学术界目前暂无 1:1 完全撞车**”。这句话在文档自己的更新日期（2026-11-10）就已经过期了。有两篇更早的论文做了完全一样的事：

**StateMem（arXiv:2608.19652，2026-08-20，UIUC）**

| 你的设计 | StateMem 对应实现 |
|---|---|
| `subject/predicate/scope` 槽位裁决 | state unit `(id, content, priority, source, deps)` |
| `CASCADE_DEMOTED` 覆盖连坐 | 确定性 **Rechecker** 沿依赖图把下游标 `needs_recheck` |
| `candidate_conflict` 挂起不自动覆盖 | 只标 supersession、保留 superseded 单元供审计 |
| 幂律衰减 | 未做（这是你确实领先的一点） |
| 结构残差直连 | 未做 |

论文原文：*"a deterministic Rechecker traverses the dependency graph G=(U,E)... sets u_i to needs_recheck, marking its content as possibly stale"* —— 这就是 `gated_mem.md:42` 的 `ψ(p)` 连坐，只是它用的是布尔标记而不是 0.15 乘子。

**MemStrata（arXiv:2606.26511 / 2608.20685，2026-06 与 2026-08）**

确定性 `(subject, relation, object)` 覆盖规则 + 双时序账本，**无相似度阈值、无 LLM 调用**。这与你 `gated_mem.md:16`（第 2 条铁律“拒绝纯余弦阈值覆盖，改用槽位对齐”）是同一个机制。而且它已经在**真实 GitHub 修复历史**上验证过：707 个 SWE-bench issue 中提取 130 个原子状态转移，MemStrata 0.91 准确率 vs RAG 0.57–0.59，stale-fact-error 从 36–38% 压到 ~0。

**这意味着什么**：
- 差异化不能再说“没人做状态跟踪”。这句话写进 README 会被审稿人和竞品直接打脸。
- 真正的空白位是有的，但更窄：**没有人把这件事做成零 API、零守护进程、可 `undo`、可审计的本地插件**。StateMem 是论文里的方法（无产品、无持久化层），MemStrata 是预印本 + 产品，但自报覆盖率只有 **18.4% 的真实修复是干净原子转移**。产品护城河在“工程形态 + 编码场景”，不在“机制首创”。

### 1.2 你的头号护城河（覆盖连坐 ψ=0.15）有已发表的负收益证据

这是本次复核最重要的一条。

StateMem 论文 §6.2 的消融直接测了“依赖传播”（= 你的连坐）这一项：

> *"dependency propagation helps its target modes but **over-propagates on Set B anti-traps (−12.5 pp)**, and **removing it leaves DeepSeek slightly better (0.373 vs. 0.363)**."*

即：把连坐整段删掉，在强 backbone 上总分反而更高。

而 `gated_mem.md:23` 把“覆盖连坐”列为三大核心创新之一，`artifacts/competitive_landscape_analysis.md:64` 把它列为“四大独家护城河”的第 2 条，`artifacts/gated_mem_workflow_guide.md:233` 称它是“核心防污染防线”。

你自己的 `artifacts/self_critique_and_landscape_enhancement.md:21-26` 其实已经识别出这个风险（“误杀中间规则”），并提出了“双态连坐 Hard/Soft”的补丁。这个补丁方向是对的，但它**只降低误杀，不解决负收益**——因为 over-propagation 的问题不是“罚得太重”，而是“罚了不该罚的”（anti-trap 模式：父级被废弃，但子规则其实仍然成立，且正是这些规则能防住陷阱）。

**建议**：把连坐从“核心机制”降级为**默认关闭的实验特性**，并且必须在自己的 fixture 上跑出“开着比关着好”才允许默认开启。不要在 README 里把它当卖点——它是目前证据最弱的一环，却排在计划的第一位。

### 1.3 “没有 ¥4100 所以不能跑评测”—— 论证路径是错的（尽管数字量级碰巧接近）

三份文档给了三个互斥的成本：

| 文档 | 说法 |
|---|---|
| `memory_plugin.md:246` | 混合档 **¥4100**（22,200 题次 × $0.026） |
| `artifacts/benchmark_guide.md:77` | DeepSeek-V3 跑完整实验 **≤ ¥20** |
| `gated_mem.md:12,21` | “**没有 ¥4100 的 API 预算**”，所以用 Golden Fixtures 替代 3-Judge |

我最初判断 ¥4,100 高估了 10–20 倍。**这个判断是错的，收回。** 按 2026-11 的实际价格重算后，¥4,100 的数量级反而是最接近的——但它**碰巧对**，因为两个错误互相抵消了：

**错误一：题量高估约 2.7–3.3×。** `memory_plugin.md:238-242` 的题次表用的是：

| 数据集 | 文档假设 | 实际（已核实） |
|---|---|---|
| StateMemBench | ≈700 题 | **322 probes**（234 场景：190 短 ×1 probe + 44 长 ×3 probes） |
| Memora weekly | ≈400 题 | **150 题** |
| Memora quarterly | ≈1000 题 | **300 题** |

**错误二：完全漏算 ingest 成本。** 这一点比题量错得严重。StateMem 是**每个对话轮都调一次 LLM**（`TurnEncoder`，one LLM call per turn）做状态抽取。StateMemBench 的 Set A 是 18 sessions / 中位 165 turns，Set B 是 38 sessions / 中位 599 turns。**光把 benchmark 灌进记忆库，就是 ~10 万次 LLM 调用**——这部分在 `memory_plugin.md:225` 的成本模型里完全不存在（它只算了“检索+回答+judge”）。

**重算（按 DeepSeek-V4-Flash 实价，$/M tokens：峰 $0.30/$1.20、谷 $0.15/$0.60）**：

| 阶段 | 估算 |
|---|---|
| 干净的检索+回答+judge 单轮全设计 | **¥110–550** |
| 加上 StateMem 式逐轮 ingest | **¥1,400–2,300** |

所以：`benchmark_guide.md:77` 的“≤¥20”**只有在纯本地 Ollama 路径下成立**，按它自己的 token 模型差 12–35 倍；`memory_plugin.md` 的 ¥4,100 量级对但成分错。

**真正的结论**（比我原先的更有力）：

`gated_mem.md:21` 用“没有 ¥4,100”论证“不做 LLM 评测”。但关键不是总额，是**这笔钱可以分阶段花**：

- **第一刀（¥0–50）**：StateMemBench 的 322 probes，只跑「纯向量 vs 槽位覆盖」两条件 ×1 次。**不含 ingest**（用 benchmark 自带的 state 标注直接建库）。这就能回答“槽位覆盖有没有用”。
- **第二刀（¥60–150）**：加生命力/连坐两条件，看 λ 消融。
- **第三刀（¥250–400）**：§5.3 的桥接实验（那个必须含 ingest，因为要模拟真实累积）。

**三刀加起来 <¥600，每一步都在砍掉一个假设。** 你不需要一次拿出 ¥4,100，你需要的是**不要在第一刀之前就决定花 7 天**。

**这是本次复核里最重要的一条建议**：`gated_mem.md` 用“经费不足”跳过了评测，直接用 50 个手写 fixture 替代；但真正的问题不是钱不够，是**这个决策把最便宜的证伪机会推到了 7 天之后**。

### 1.4 最严重的一条：已发表证据显示“持久化存储”在目标基准上不产生增量价值

这一条独立放在第 1 章，因为它质疑的不是某个机制，而是**项目的存在前提**。

StateMem 论文 §6.4 的 Table 6 做了一个“Wrapper”实验：**不做任何持久化存储**，只把状态跟踪做成一次 prompt 改写（先 trace 出每个槽位值变更链，再按四条优先级规则 resolve），接在**已有的** memory backend 上，**不增加任何 LLM 调用**。

结果（StateMemBench，n=60 配对子集，同一批检索到的 chunk、同一个 judge）：

| 条件 | Qwen-3.5-9B | DeepSeek-V4-Flash |
|---|---|---|
| 完整 StateMem 系统（有持久化存储） | **23.3** | **36.3** |
| Mem0 单独 | 25.0 | 28.3 |
| Mem0 + **纯 prompt Wrapper** | **56.7** | **71.7** |
| A-Mem + Wrapper | 56.7 | 75.0 |
| Dense + Wrapper | 56.7 | 70.0 |

**纯 prompt 改写拿到 56.7–75.0，比完整持久化系统（23.3–36.3）高约 2 倍。** 而且论文明确说 wrapper 对**六个 backend 全部有效**、十二个 cell 全部显著（McNemar p≤0.04）。

论文自己的解释：

> *"the wrapper outperforms StateMem itself on the same scenarios... When the transcript fits in context, **resolving state at answer time is good enough**, but the persistent store can be useful when it **does not fit**."*

**这句话对你的项目是双刃的：**

**不利的一面**：StateMemBench 的历史长度是 165–600 turns / 3k–15k tokens。在这个 regime 下，**任何能装下全文的上下文就够了**，你的 SQLite、事件溯源、幂律衰减、连坐、残差**全部不产生增量价值**。所有“检索层”指标——包括 `gated_mem.md:158` 计划花 7 天做的那些——**都测不到存储赚回成本的那个 regime**。

**有利的一面**：它精确定位了**你唯一可能赢的地方**——**历史装不进上下文窗口的时候**。而这是真实编码项目的常态：一个中型项目三个月的架构决策史，加上每次决策的上下文，远不止 15k tokens。论文明确承认持久化存储在“装不下时有用”，但**没有测那一点**。

**那里是一块没人占过的地。**

**这意味着三件事必须改**：
1. **不要在 StateMemBench 上宣称“优于 StateMem”**——它测的是短历史，你的优势不在那儿，而且你的架构（事件溯源 + 衰减）在那个 regime 下大概率还不如一次性 prompt 改写。
2. **桥接实验必须跑两个 token regime**（见 §5.3），并且**判定标准挂在 regime(b) 的增量上**，不是总平均。
3. **README 的定位要改**：不是"更好的记忆"，是"**历史装不下时的记忆**"。这个定位有理论依据（Table 6 的边界），竞品也覆盖不了（它们没有持久化状态层）。

## 2. 方案里真正有价值、不要在重构中丢掉的东西

复核不是只挑毛病。以下四点是这份方案里真正稀缺的判断，有些甚至在竞品那里是缺的：

**① 事件溯源 + `before_state` 快照作为底盘。**
`gated_mem.md:15,103`。这是所有竞品都没有的（`artifacts/competitive_landscape_analysis.md:26` 这张对比表在这行是对的：Graphiti 依赖数据库事务回滚、Mem0 无法无损回滚、claude-mem 无撤销）。对一个**会自动判断新旧的系统**来说，“判错了能一键回滚”不是锦上添花，而是敢不敢开自动化的前提。这条要保住，并且要作为产品第一卖点重写（现在的文案把它排第四）。

**② “未回传 ≠ 未使用，废除 IGNORED 自动降权”。**
`gated_mem.md:17`。这是个非显然且正确的判断。宿主 LLM 经常不回传 `cited_ids`，负面约束（“禁止用 Redis”）在回答里根本不留痕迹。任何把“没被引用”当负标签的设计都会系统性杀死否定式约束——而否定式约束恰恰是编码 agent 最需要记住的那类记忆。多数记忆插件在这里都做错了。`project_plan.md:282-289` 把这条写成了硬规则，很好。

**③ “向量只找候选，槽位决定覆盖；拿不准就挂起”。**
`gated_mem.md:171`。这条纪律是对的，而且有独立证据支撑：MemStrata 测出余弦相似度区分“矛盾”和“重复”的 **AUROC 只有 0.59**（接近随机），而且矛盾往往比改写**更像**原句。所以任何基于相似度阈值的覆盖判定，从原理上就不可能做对。你这条规则不是保守，是正确。

**④ `residual_diff`（记住为什么变，而不只是变成了什么）。**
`gated_mem.md:51-54`。这是全文最有产品感的设计，也是文档里最欠规格的一处：没有字段 schema、没有写入协议、没有评测指标、没有 UI 呈现规则。而它恰好对应一个真实高频的开发者行为——**“我们当初为什么不用 MySQL？”**。StateMem 和 MemStrata 都没有做这个。如果要选一个点做深，我选它。

## 3. 架构层面的硬缺陷：不改就无法实现

以下每一条都是“照现在的文档写代码会卡住”的级别，不是风格问题。

### 3.1 缺少检索排序方程（最严重）

`gated_mem.md:37-42` 定义了生命力 $F_t(v)$，`gated_mem.md:132` 说“在固定 Token 预算内完成”检索。但**从头到尾没有给出“相关性 × 生命力 → 最终选谁”的方程**。

$F_t$ 是一个**不带查询的**量（只依赖 $\Delta$、祖先状态、残差边）。检索还需要一个**带查询的**相关性分数。两者怎么合并？

- 相乘？一条强相关但已衰减到 0.2 的记忆，会输给一条无关但新鲜的记忆（$F \approx 1.0$）。
- 先过滤后排序？那阈值是多少？谁来定？
- 加权求和？权重怎么定？

**这是 Day 1 就要写的第一行代码，而文档里没有它。** 建议明确定义为：

```
score(v|q) = rel(q, v) · [ F_t(v) ]^λ        λ ∈ [0,1]，λ=0 退化为纯向量
```

并用 λ 作为消融项之一（λ=0 / 0.3 / 1.0 三档）。这个 λ 本身就回答了“门控到底有没有用”这个核心问题——如果 λ=0 和 λ=0.3 没差别，整个生命力体系可以删掉。

### 3.2 `input_weight` 是装饰品

`gated_mem.md:72` 在 schema 里声明了 `input_weight REAL NOT NULL -- 初始写入重要度 i_t`。但 `gated_mem.md:37-42` 的 $F_t(v)$ 公式里**没有任何一项用到它**。

也就是说，“输入门 $i_t$”在数学上不存在，只存在于 `memory_plugin.md:21` 那张 LSTM 对照表里。而“门控分离”是这个项目对外宣称的第一个卖点（`memory_plugin.md:90` “不能用一个 importance 分数同时管写入和淘汰”）。

**要么把它写进公式**（例如 $F_t(v) = i_v \cdot (R + \dots)$，或作为 $t_0$ 的缩放因子 $t_0(v) = t_{0,\text{type}} \cdot i_v^{\eta}$），**要么就承认首版没有输入门**，别在文档里留着。按现在的写法，实现者会不知道这个字段该读到哪儿去。

### 3.3 “O(1) 一键 undo”不成立 —— 而且按现有 schema 根本做不到

`gated_mem.md:15` “只需一行 `gated-mem undo <event_id>` 即可 100% 无损回滚”、`gated_mem.md:103` “确保 O(1) 逆向撤销”、`artifacts/gated_mem_workflow_guide.md:355` “瞬间无损回滚整个图谱拓扑”。

三处都写了 O(1)，三处都不对，而且问题比“复杂度写错”严重得多：

1. **事件表没有因果链字段，派生事件在物理上查不到。**
   `gated_mem.md:98-105` 的事件表只有 `event_id / project_id / step / event_type / payload_json / created_at`。**没有 `causation_id`，也没有 `parent_event_id`。**
   撤销 `MEMORY_SUPERSEDED(#103)` 时，必须找到它派生的那一批 `CASCADE_DEMOTED` 事件。但在现在的 schema 下，一条 `CASCADE_DEMOTED` 和触发它的 `#103` 之间**没有任何外键关系**。
   `artifacts/gated_mem_workflow_guide.md:349` 说“利用 payload_json 中的 before_state 快照……并**逆向消除 104 连坐**”——做不到。你连 104 是哪几条都不知道，除非事先把整批 ID 塞进 #103 的 payload（那 payload 就是 O(N) 的）。
   **这是 schema 缺字段，不是实现偷懒。**

2. **撤销语义未定义。** 如果 #103 之后已有 #105 基于“MySQL 已废弃”这个事实写入了新记忆，撤销 #103 后 #105 怎么办？文档没写。事件溯源系统必须回答“补偿事件 vs 全量重放”这个二选一。

3. **事件表无 compaction 策略。** `RECALL_DELIVERED` 是**每次查询**都写一条（`gated_mem.md:102` 的 event_type 列表里有），和状态迁移混在同一张不可变表里。跑三个月后事件表是状态表的上千倍，启动重放会明显变慢。

### 3.3b 补充：连坐乘子的量级被严重低估

`gated_mem.md:42` 说 ψ 从 1.0 变为 0.15 后“子节点总生命力立刻被压缩至 15% 以下”（`artifacts/gated_mem_workflow_guide.md:233` 同样表述）。

但公式是**连乘** $\prod_{p \in \mathcal{A}(v)} \psi(p)$：

| 被覆盖的祖先数 | $\psi^k$ |
|---|---|
| 1 | 0.15 |
| 2 | **0.0225** |
| 3 | **0.003375** |
| 4 | **0.000506** |

在真实的多父 DAG 里（`workflow_guide.md:203-234` 明确支持多父），一条交叉衍生规则很容易有 2–3 个被废弃的祖先。“压缩至 15% 以下”这句话技术上不算错，但它**掩盖了实际是压缩到千分之三**这个事实——这正是 §1.2 里 StateMem 测到的 over-propagation 的数学来源。文档应该直接写明“多父情况下按 0.15^k 指数衰减”，让人一眼看到这个设计有多激进。

### 3.3c `BELONGS_TO` 的边方向在文档里是矛盾的（会直接写反遍历）

这是最隐蔽但杀伤力最大的一条：

- `gated_mem.md:90`：`source_id -- 起点`、`target_id -- 终点`，而 `gated_mem.md:119` 说“挂载到对应 Scope 父节点 (BELONGS_TO)”——按这个读法，边是 **子 → 父**。
- `artifacts/gated_mem_workflow_guide.md:90`：“节点的物理层级等于它沿 `BELONGS_TO` 边追溯到 `ROOT` 的**最短有向跳数**”——要求边是 **子 → 父**，才能从子追溯到根。
- 但 `artifacts/gated_mem_workflow_guide.md:192-196` 的 Mermaid 图和 `:216-217` 的 `PA -->|BELONGS_TO| Child` 画的是 **父 → 子**。

三种读法，两个方向。级联遍历（“遍历旧记忆的所有子节点”，`gated_mem.md:124`）和深度计算（“溯源到 ROOT”）需要的是**相反方向**的边。

**建议**：统一为 `child --BELONGS_TO--> parent`（source=子，target=父），因为：
- 深度计算是沿 target 向上走，符合“溯源”语义；
- 级联降权需要“找所有子节点”，此时建一个反向索引（SQLite 上就是 `CREATE INDEX ON memory_edges(target_id)`），一次索引扫描 O(log N)，比存两套边干净。

如果实现者照 `workflow_guide:216` 的图画，级联会**反向传播**（父节点被连坐、子节点被提权），而且不会报错——只是行为全错。这类 bug 在测试里极难发现。

**建议**：
- 把 `RECALL_DELIVERED` 挪到独立的 `recall_log` 表（可轮转、可截断），不要进不可变事件流。
- undo 明确为**生成补偿事件**（`EVENT_UNDONE` + 一组恢复事件），复杂度写实为 O(受影响的子树)，不要吹 O(1)。
- 定义 undo 的前置检查：若目标事件之后存在依赖其结果的后续事件，**拒绝并提示**，而不是静默连锁撤销。
- 加 **snapshot**：每 N 个事件或每天落一次全量快照，`replay` 从最近快照开始。

### 3.4 状态机不闭合

`gated_mem.md:71` 给了 5 个状态：`active | candidate_conflict | superseded | archived | killed`，但**没有迁移表**。至少这些是空的或矛盾的：

- `candidate_conflict` 解决后去哪？用户选“新的对”→ 新的转 active、旧的转 superseded；用户选“两个都对但作用域不同”→ **没有状态能表达“两个都 active 但互斥”**。现在只能分别改 scope，这是隐式的、不可审计的操作。
- `archived` 和 `superseded` 的区别是什么？谁能进谁？
- `killed` 能否复活？`project_plan.md:283` 说“Kill 不被普通反馈复活”，但 `gated_mem.md` 完全没这条规则——两份文档不一致。

**建议**：补一张 5×5 迁移矩阵，每个格子写“允许/拒绝/需要什么事件”。这张表比任何公式都更能防止实现期跑偏。

### 3.5 `pinned` 与 `ψ(p)` 的规则冲突

`artifacts/gated_mem_workflow_guide.md:238` 说 pin 之后“锁定节点生命力强制为 1.0，直接免疫一切连坐与时间衰减”。

但 `gated_mem.md:39` 的公式是：

$$F_t(v) = (\dots) \times \prod_{p}\psi(p)$$

**没有 `pinned` 项。** 按公式，pinned 节点照样被祖先连坐压到 0.15。按文档，pinned 节点免疫一切。

这是文档内部的直接矛盾，而且会在第一个真实用例上炸：用户 pin 了“单测必须 mock 外部依赖”这条通用规则，然后把 Redis 换掉了，这条规则被连坐杀死了——这正是 `self_critique...md:26` 描述的灾难场景。

**修法**：公式改成

$$F_t(v) = \begin{cases} 1 & \text{pinned} = 1 \\ (\dots)\times\prod_p \psi(p) & \text{otherwise} \end{cases}$$

但这会引入新问题：pin 可以被当作“永久正确性”滥用，且 pin 后时间衰减也停了。建议至少把 **pin 的免疫范围收窄到只免疫 ψ，不免疫 R**——即 pin 的规则仍然会因为久未使用而降低排序优先级，只是不会被覆盖连坐杀死。这个区分很重要，现在的“免疫一切”是过度设计。

### 3.6 多父 DAG 的扩散没有收敛定义

`gated_mem.md:39` 的正向扩散项是 $\sum_{u \in \mathcal{N}_\text{parent}(v)} \gamma \cdot \mathbb{I}(u) \cdot F_t(u)$，**递归依赖父节点的 $F_t$**。

- 如果 DAG 存在环（`BELONGS_TO` 边的建立规则在 `workflow_guide.md:100` 是“由 Scope 路径决定”，没有防环检查），递归不终止。
- 即使是 DAG，菱形结构下同一祖先会被多次计算（路径数级）；没有记忆化/拓扑排序的定义。
- 数值上：γ=0.3，深 4 层时贡献是 $0.3^4 \approx 0.008$。**这个量级对最终排序毫无影响**，等于白算。要么把 γ 提到 0.6–0.8（但那样浅层会淹没深层），要么承认“多跳扩散在深度 ≥3 时无意义”，只做 1 跳。

**建议**：明确写“只做 1 跳扩散”（$\mathcal{N}_\text{parent}$ 只取直接父节点，不再递归），并在建边时做环检测。1 跳已经能拿到全部收益，多跳纯属浪费 CPU 且会引入不可解释的分数。

### 3.7 并发与写入路径没有设计

`gated_mem.md` 全文假设单进程。但实际部署是：Claude Code Hooks（`SessionStart`/`Stop`）+ MCP Server（stdio，可能多开）+ CLI + Web UI（`gated_mem.md:150` 支持点击 Pin/Kill/Undo）。**四个进程写同一个 SQLite。**

`project_plan.md:326-329` 明确写了 `busy_timeout`、短事务、单写者/写入队列、同一逻辑事务提交。`gated_mem.md` 一个字都没有。

**建议**：直接采纳 `project_plan.md:6.2` 的工程约束，不要重写。

### 3.8 一条会直接失败的 Day-1 单测：`R(2H) = 0.25` 是错的

`project_plan.md:234` 把 `R(2H) = 0.25` 列为必须覆盖的单元测试。但这个期望值来自**指数**衰减的直觉（每过一个半衰期减半），而文档自己在 `:210-216` 明确规定的是**幂律**：

$$R(\Delta)=\left(1+\frac{\Delta}{t_0}\right)^{-\beta}, \qquad H=t_0\left(2^{1/\beta}-1\right)$$

代入 $\Delta = 2H$：

$$R(2H)=\left(1+2\cdot\frac{H}{t_0}\right)^{-\beta}=\left(2\cdot 2^{1/\beta}-1\right)^{-\beta}$$

实算（$t_0=1$）：

| $\beta_{\text{type}}$ | $R(H)$ | $R(2H)$ |
|---|---|---|
| 0.5 | 0.5 | 0.4142 |
| 1.0 | 0.5 | **0.3333** |
| 2.0 | 0.5 | **0.2991** |
| 5.0 | 0.5 | **0.2752** |
| → ∞ | 0.5 | → 0.25（仅极限） |

**只有 $\beta \to \infty$ 才趋近 0.25，任何有限 $\beta$ 都严格大于 0.25。**

两个后果，都不小：
1. **Day-1 验收直接失败**（`gated_mem.md:146` 的验收标准是“单元测试 100% 通过”）。开发者在第一天就会遇到一个“公式没错、测试错”的挫败点，最常见的错误反应是**改公式去迁就测试**，也就是把已经正确选定的幂律改回指数——恰好毁掉 `memory_plugin.md:113-119` 用整整一节论证过的设计。
2. 它暴露了一个更本质的误解：**幂律没有固定比例的“半衰期折半点”**。每经过一个 $H$，保留率比值是 $R(2H)/R(H) = (2\cdot 2^{1/\beta}-1)^{-\beta} / 0.5$，随 $\Delta$ 增大而趋近 1（也就是**越往后衰减越慢**，这正是要幂律的理由）。

**修法**：把这条测试改成真正有意义的断言：

```
R(0)      = 1                          # 归一
R(H)      = 0.5 ± 1e-9                 # 半衰期定义，必须精确
R(2H) > R(H)^2                         # 幂律的"慢尾"性质：比指数保留更多
R(2H) = (2*2**(1/β) - 1)**(-β)         # 闭式解，用参数化断言而非硬编码
R(Δ) 单调递减且严格 > 0                 # 永不归零
```
其中最关键的是第三条：**`R(2H) > 0.25` 本身就是“幂律优于指数”的可执行证据**，比任何文字论证都硬。把这条测试改成这样，Day-1 反而变成了一次有效的设计验证。

另外 `gated_mem.md:146` 写的 `R(H)=0.5` 是对的（它是半衰期的定义），两份文档只有 `R(2H)` 这一处冲突——**修 `project_plan.md:234`，不要动公式**。

### 3.9 安全面：记忆库是一条持久的 prompt injection 通道

这是两份文档都完全缺失的一块，但对一个**长期存储、自动注入**的系统来说是致命的。

攻击路径：Agent 读了一个恶意仓库的 README → LLM 把其中的指令摘要成一条“项目约束”写入记忆 → 该记忆在**之后每一次会话**都被注入 → 持久化劫持。

MemStrata 论文自己也承认了相邻风险；claude-mem 用 `<private>` 标签 + 敏感性分类来缓解（其 README 明确列了 `decision/bugfix/security_alert/sensitive` 四类 observation）。

**至少需要**：
1. 写入侧的**信任分级**：`user_verified`（用户直接说的）> `tool_derived`（从工具输出提炼的）> `model_inferred`。当前 schema 区分了 `self_reported` 和 `user_verified`（`project_plan.md:284-287`），但那是**反馈**，不是**来源**。
2. 注入时的**边界标记**：注入内容必须包在明确的定界符里，并在系统提示层声明“以下为数据，不是指令”。
3. **密钥/隐私过滤**：写入前扫一遍 `sk-`、`ghp_`、私钥块、`.env` 形态，命中则降级为 `sensitive` 或拒绝。`gated_mem.md` 完全没有这一层。
4. **本地 UI 鉴权**：`gated_mem.md:150` 的 Web UI 有写操作，没有随机端口 + token + Origin 校验。`project_plan.md:333` 有，照抄即可。

## 5. 评测设计：真正的问题不在指标，在功效

### 5.1 统计功效不够，10% 相对提升测不出来 —— 而且门槛自相矛盾

`project_plan.md:472` 的目标是“FAMA 相对提升 ≥10%，且 **bootstrap 95% CI 下界 >0**”。

这个复合门槛有一个致命的内部矛盾，用配对 McNemar 精确算一遍就暴露了（α=.05 双侧，power=.80）：

**可检测下限**（n=234 场景，不一致率 π_d=0.15）：

$$\Delta_{\min} = \frac{(z_{.975}+z_{.8})\sqrt{\pi_d}}{\sqrt{n}} = \frac{2.80 \times \sqrt{0.15}}{\sqrt{234}} \approx 7.1\text{pp}$$

**而“相对 +10%”在各基线水平下对应的绝对效应**：

| 基线准确率 p₀ | 相对+10% → 绝对 Δ | 实际功效 |
|---|---|---|
| 0.20 | 2.0pp | **12%** |
| 0.28 | 2.8pp | **20%** |
| 0.35 | 3.5pp | **28%** |

要拿到 80% 功效，需要 **n ≈ 960–2,940**。StateMemBench 只有 322 probes，×3 次重复也不能增加有效样本量（重复只降方差，不增独立观测）。

**更严重的是第二半句**：要在 n=234 上让 **CI 下界 > 0**，观测到的效应必须 >4.96pp（≈17.7% 相对）。

**也就是说：即使你的方案真实有效、且正好达到它自己设定的“+10% 相对提升”，这道门也必然判失败**——因为 10% 相对提升的效应量（2–3.5pp）远小于 CI 下界>0 所需的最小效应（4.96pp）。

**这不是“样本量偏小”，这是门槛在数学上自相矛盾。** 一个永远不会通过的验收标准，等于没有标准——最坏的结果是开发者在 D7 面对失败时无法区分“方案不行”和“测试设计不行”。

**建议**（三处必须同时改）：
- **A**：把点目标从“相对 +10%”改成**绝对 +7pp 以上**（这样 n=234 刚好可检测），或明确写“预期效应量 ≥0.15pp/题”。
- **B**：**删掉“CI 下界 >0”这个硬门槛**，改成“报告 CI 宽度；若 CI 跨 0，则扩大样本或降级为方向性结论”。把“显著性”当 Go/No-Go 条件，在小样本上必然导致要么永远不 Go、要么 p-hacking。
- **C**：如果坚持要测 10% 相对效应，就必须**自建 ≥1,000 题的编码集**（这正好是 `gated_mem.md:160` 的 `Golden-Coding-Evolution-50` 该有的规模，不是 50）。

对比：StateMem 论文报告的是 **+15.8pp 绝对**（0.205→0.363），那是一个 n=322 就能测出、McNemar p<0.001 的大效应。**你的目标效应量比已发表的 SOTA 提升小了 5 倍，却用同一个基准去测**——这才是根本问题。
- **B**：自建 ≥1,500 题的编码演进 fixture（这正好是 `gated_mem.md:160` 的 `Golden-Coding-Evolution-50` 该有的规模，不是 50）。

我推荐 **A + B + C 的组合**：先用公开基准证明机制有效性（绝对口径，n=322 够用），再用自建 ≥1,000 题编码集证明产品价值（`project_plan.md:420` 已经意识到了“不能由通用对话基准替代”，但没给规模）。

### 5.2 缺的是桥接实验，不是更多 benchmark

`project_plan.md:420` 写了“真实编码项目集”但没设计。而这是整个方案最关键的空白：**所有 benchmark 评的都是“检索注入层”，产品的承诺却是“少写错代码”。这中间没有任何实验。**

更要命的是，这个桥接**已经有人做了一半，结果是负面的**：Reddy & Challaram（arXiv:2606.01435）在 MemoryAgentBench 上做受控全流水线对比，结论是：

> *"changing only the final policy executor contributes **2.0 pp** on average and **0 pp at 262K**. Most of the gain therefore comes from **separating evidence identification from final policy execution** rather than from the freshness operator itself."*

翻译：把“时效判定”这一层单独换掉，只值 2 个点；值钱的是“把证据识别和策略执行分开”这个**结构**。而 `gated_mem.md` 的工程量 80% 压在“时效判定”（衰减公式、连坐、残差），20% 在结构（Explain Receipt）。**比例是反的。**

同一篇论文还给了个冷水：在 LongMemEval 上这类修复**没有显著优势**（26/45 vs 29/45，p=0.45）。

### 5.2b 这个 benchmark 在设计上测不到“存储”的价值

**完整论证见 §1.4。** 这里只补一句方法论后果：因为 Table 6 显示短历史下纯 prompt 改写碾压持久化系统，所以**任何只在一个 token regime 上跑的实验都无法区分"记忆架构"和"prompt 质量"**。桥接实验必须双 regime（§5.3），且判定标准挂在"装不下"那个 regime 的增量上。

### 5.2c “过期泄露率 <2%” 是个反向指标，必须删掉

`gated_mem.md:164` 的目标是“传统向量基线 >40%，本方案 <2%”。

StateMemBench 自己的 Table 5 给出了反例：

| 方法 | in-pool 数 | drift-rate |
|---|---|---|
| full context | 258 | 64.0% |
| Mem0 | 268 | 59.9% |
| StateMem（完整方案） | 286 | **49.1%** |
| **LightMem** | **52** | **14.9%** ← 全场最低 |
| MemoryOS | — | 25.0%（accuracy 0.025） |

**LightMem 的 drift-rate 只有 14.9%，看起来远好于 StateMem 的 49.1%，但它的 accuracy 只有 0.012，322 个 probe 里只有 52 个落在 in-pool。**

论文 §6.3 的原话警告：

> *"Methods that answer predominantly off-pool... **post deceptively low drift-rates by construction**, not because they resist the drift target trap but because they rarely produce an in-pool (plausible) answer."*

**也就是说：“过期泄露率低”可以通过“大量拒答 / 解析失败 / 输出不匹配任何选项”来伪造。** 一个只回答 3 道题且全对的系统，泄露率是 0%，但它是废的。

**后果**：如果你把 <2% 写进 README 做卖点，任何人翻到 StateMemBench 第 6.3 节一页就能推翻——而且是用**你自己引用的那篇论文**。这比“数字偏高”严重得多，它是**指标本身指错了方向**。

**修法**：任何泄露率指标都**必须和 in-pool 率 / 有效作答率一起报**，且主指标应该是 StateMemBench 的 closed-pool accuracy（因为它同时惩罚 drift 和拒答）。写成：

```
主指标：Current-State Accuracy（closed-pool，同时惩罚 drift 与 off-pool）
辅指标：Drift-rate（标注 in-pool 数，禁止单独报告）
```

这比“泄露率 <2%”难看得多，但它是**唯一不会被一页纸推翻**的写法。

### 5.3 桥接实验的最小可行设计（已按 §5.2b 修订）

给一个能在 2–3 天内跑完、成本 <¥400 的设计。**关键是必须包含“纯 prompt 改写”这个对照臂**——否则赢了也不算，因为你不知道赢的是存储还是 prompt。

| 项 | 设计 |
|---|---|
| **任务** | 沿用 arXiv:2610.30571 的范式：40 个小项目，每个项目的 `CLAUDE.md` 里写一条**已过期**的约定（例：“用 print 不要用 logging”），而现有代码用的是相反约定 |
| **为什么用它** | 这篇论文实测：**90.1% 的 agent 选择跟随过期指令文件**，即使它明确指出了冲突（Claude Code 在 80 次里指出 79 次冲突，仍然照做）。这是**真实、可测、已发表的基线** |
| **关键设计** | 必须跑**两个 token regime**：(a) 历史能装进上下文（~5k tokens）；(b) 历史**装不进**（30+ 轮演进，~40k tokens）。**只有 (b) 能体现存储的价值**（见 §5.2b） |

**五臂对照**（这是修订的核心）：

| # | 条件 | 检验什么 |
|---|---|---|
| ① | 无记忆（纯 `CLAUDE.md`） | 基线：问题存在吗 |
| ② | 纯向量检索记忆 | 最常见竞品做法 |
| ③ | **纯 prompt 状态改写**（无存储，每次现算） | **最关键的一臂**：StateMemWrapper 式做法 |
| ④ | Gated-Mem 完整方案 | 你的方案 |
| ⑤ | 一行用户级指令（论文的 one-sentence fix） | 最便宜的替代方案 |

**为什么 ③ 和 ⑤ 都必须在**：
- 少了 **③**，你无法证明花 7 天做的存储/事件溯源/衰减比“每次现算一遍”更好。§5.2b 显示 ③ 在短历史 regime 下**碾压**完整系统。
- 少了 **⑤**，你无法证明这个插件值得装。论文实测 ⑤ 把跟随代码的比例从 4.2% 提到 **91.4%**，测试通过率 89.4% → **100%**。**如果 Gated-Mem 打不过一行话，这个产品就没有存在理由。**

| **指标** | 主：agent 最终代码是否与**当前事实**一致（二值，可自动判）；次：项目自带测试通过率；三：注入 token 数；四：**regime (b) 下相对 ③ 的增量** |
| **样本量** | 40 项目 × 5 臂 × 2 重复 = 400 runs。按 §5.1 的功效，可检测 **Δ≥8pp**（配对，π_d=0.15） |
| **成本估算** | 约 24M tokens（两 regime 合计），DeepSeek 档 ≈ **¥250–400** |

**判定逻辑（提前写死，防止事后解释）**：

```
若 ④ ≤ ③ 且 ④ ≤ ⑤                → 停止。存储这一层不产生价值。
若 ④ > ③ 但 ④ ≤ ⑤                → 转向。价值在状态结构，产品形态应是 prompt/skill 而非插件。
若 ④ > ⑤ 且 regime(b) 增量 > regime(a) → Go。存储价值确认。
若 ④ > ⑤ 但两 regime 增量相同         → 可疑。可能是 ④ 里的某个 prompt 在起作用，
                                        而非存储本身（需进一步消融）。
```

**最后一行最容易被忽略**：如果两个 regime 的增量一样，说明你赢的是 prompt 质量而不是记忆架构。那种情况下，正确答案是把那个 prompt 做成开源模板，而不是做一个插件。

这个实验的价值：**它会在 3 天内告诉你，你要做的产品是不是一个问题，以及你的方案是不是那个答案**。比做完 7 天 MVP 再发现要值钱得多。

### 5.4 目标数字定得太满

| 目标 | 出处 | 问题 |
|---|---|---|
| 过期泄漏率 **<2%**，基线 >40% | `gated_mem.md:164` | MemStrata 做到 ~0，但**只在 18.4% 的真实修复上**（干净原子转移）。StateMemBench 上最强方法 current-state accuracy 只有 0.363。把 <2% 当宣传数字，会在第一次被要求复现时翻车 |
| 误覆盖精度 **≥98%** | `project_plan.md:483` | 200 对样本里 98% = 最多 4 个错误。这个精度**要求自动覆盖几乎不出错**，实质上等于“永远人工确认”。如果达不到就永久保留人工确认，那这条门槛写的其实是“不要做自动覆盖” |

### 6.3 改（给出可直接落地的规格）

**① 补检索方程，把 λ 变成第一个消融项**

```
score(v|q) = rel(q,v) · F_t(v)^λ
λ ∈ {0, 0.3, 1.0}    # λ=0 即纯向量基线
```

**这是整个项目的判定性实验**：如果 λ=0.3 与 λ=0 在 StateMemBench 上无显著差异，生命力体系整个删掉，项目转向“纯槽位状态覆盖 + 撤销”。这个实验 3 天能跑完，成本 <¥60。

**② 把 `input_weight` 接进公式**

$$t_0(v) = t_{0,\text{type}} \cdot \left(\frac{1}{i_v}\right)^{\eta}, \quad \eta \in [0,1]$$

即写入重要度越高，半衰期越长。η=0 退化为现在的按类型固定。**这样“输入门”才真实存在于数学里**，而不是只活在对照表中。

**③ 状态机补迁移表**

| from \ to | active | candidate_conflict | superseded | archived | killed |
|---|---|---|---|---|---|
| active | — | 新证据矛盾 | 显式覆盖 | 容量驱逐 | 人工/规则 |
| candidate_conflict | 用户裁决 | — | 用户裁决 | 超时归档 | 人工 |
| superseded | **仅 undo** | ✗ | — | 归档 | 人工 |
| archived | **仅 undo** | ✗ | ✗ | — | 人工 |
| killed | **仅 undo** | ✗ | ✗ | ✗ | — |

关键规则：**`killed` 和 `superseded` 只能通过 undo 复活**，不能被普通写入或反馈推翻（这是 `project_plan.md:283` 的规则，搬过来）。

**④ pin 的免疫范围收窄**

```
if pinned:  F = F_t_without_cascade(v)   # 免疫 ψ，不免疫 R
```
即 pin 保护的是“不被覆盖连坐杀死”，不是“永不衰减”。防止 pin 被滥用成“永久正确”。

**⑤ Undo 语义写实**

```
undo(event_id):
  1. 检查该事件之后是否有事件引用其 post_state
     - 有 → 拒绝，输出依赖链，提示 --force 需人工确认
  2. 生成补偿事件 EVENT_UNDONE(target=event_id)
     + 恢复事件（每个受影响节点一条，携带 before_state）
  3. 复杂度：O(受影响子树)，不是 O(1)
  4. 每 N 事件落快照，replay 从最近快照开始
```

**⑥ 写入来源分级（安全）**

```
source_trust ∈ {user_verified, tool_derived, model_inferred}
  注入优先级：user_verified > tool_derived > model_inferred
  任何 model_inferred 且命中断言/祈使句形态的写入 → 需人工确认
  secret_scan(content) 命中 → 拒绝写入或标 sensitive
```

**⑦ 加一个“演进问答”评测（`residual_diff` 的专属指标）**

这是 `residual_diff` 唯一能被验证的方式，也是竞品没有的东西：

- 构造 100 组“A→B 覆盖”序列，每组带一句变更原因
- 提两类问题：**当前态问题**（“现在用什么？”→ 答 B）和**演进问题**（“为什么不用 A？”→ 答原因）
- 指标：`Evolution Answer Accuracy`（只给 Gated-Mem 打，因为它只有它有数据）
- 对照组：无记忆 / 纯向量（它们答不出演进问题——**这就是差异化的证据**）

这个实验只花半天，但它能产出一条竞品无法复现的结果，比“过期泄漏 <2%”有说服力得多。

## 8. 引用准确性：有四处需要修，其中一处影响核心论证

`memory_plugin.md` 的调研质量整体不错，它在 §附 里也主动标注了可靠性分级（这很专业）。但复核时发现四处引用与一手来源不符，其中一处**正在支撑一条核心设计主张**：

### 8.1 FadeMem 用的是 stretched-exponential（Weibull），不是幂律，也不是纯指数

`memory_plugin.md:130` 写：

> 依据：FadeMem（arXiv 2601.18642）双层差分衰减，超过 Mem0 且**存储省 45%**。

它被放在 §3.3「衰减用幂律，不用指数」的末尾作为该节的依据。有三处不准确：

1. **衰减形式**：FadeMem 摘要原文是 *"retention is governed by adaptive **exponential** decay functions"*，但其实现用的是 **stretched-exponential / Weibull 形式**（β=0.8 / 1.2）。这既不是纯指数，也不是幂律。**用它给“必须用幂律”背书，是范畴错误。**

2. **“超过 Mem0”的幅度被夸大了**：在 LoCoMo 上 FadeMem 对 Mem0 是 **+1.06 F1（28.37 → 29.43，+3.7%）**。这不叫“超过”，叫“持平或略好”。把它写成“超过 Mem0 且存储省 45%”，会让读者以为是个显著优势。

3. **“存储省 45%”的口径**：那个数字来自 *Multi-Session Chat / LoCoMo / LTI-Bench* 上“主动遗忘 vs 不遗忘”的对比，**不是“幂律 vs 指数”的对比**，也不是“vs Mem0”的对比。

**后果**：§3.3 的结论本身可能是对的（幂律确实更适合长周期），但它现在**只有一个论证（艾宾浩斯曲线的类比）+ 一个错误的引证**。而 §3.3 又直接决定了 `project_plan.md:234` 那条 `R(2H)=0.25` 的错误期望值（见 §3.8）——两个问题源自同一处。

顺带一个观察：FadeMem 用的 Weibull（$\exp(-(\Delta/\lambda)^\beta)$，β=0.8）在数学上**恰好介于指数和幂律之间**——它的 β<1 使尾部比纯指数长。如果作者选 β=0.8 是为了拿到“比指数更长的尾巴”，那他们的实验其实**间接支持了“纯指数衰减太快”这个判断**，只是没走到幂律。这比“FadeMem 证明要用幂律”准确，也比它更有说服力。

**修法**：
- 把 FadeMem 从“幂律的依据”挪到**“按类型分层衰减的依据”**（这一条它是真的支持：`memory_plugin.md:121-128` 的按类型分层，对应 FadeMem 的 differential decay across dual-layer）。
- 幂律的论证改为**自证**：用 §3.8 的 `R(2H) > 0.25` 这条可执行断言去实证，而不是引一个用 Weibull 的论文。
- 如果真要引证据，应该引**你自己的 StateMemBench 消融**——那才是这个项目的直接证据。

### 8.2 “LoCoMo 94% / LongMemEval 85%” —— 数字属实，但推论被实测反驳

我最初判断这个数字找不到一手来源。**这个判断错了，收回。** 子代理核查确认：这两个数字**能在 Memora 论文 §1 原文找到**（ACL 2026 Findings）。

但这条论证链的**后半段**有问题。`memory_plugin.md:167` 用它推出：

> **我们的遗忘机制在这些数据集上根本不会被触发。**

这个推论是被实测**直接反驳**的。StateMem 论文 §3.2 的标题就是“**Drift Persists Under Perfect Retrieval**”：

> *"On LongMemEval oracle, recall is 1.0 by construction, so no residual failure can be retrieval in disguise. DeepSeek-V4-Flash fails 36 of 306 questions; judges from two model families both confirm **44.4% (16/36)** as state drift — the largest confirmed failure category under guaranteed evidence."*

即：**在检索完美、且每题只需一两个 session 的 LongMemEval 上，44.4% 的失败仍然是状态漂移**。而且论文还发现漂移集中在“决策整合多个来源”的场景——多 session 问题漂移率（71.4%）接近知识更新问题（25.0%）的三倍。

**所以“多 session 少 ⇒ 遗忘机制不会被触发”这个推理不成立。** 遗忘机制的触发条件是“**事实被修订**”，不是“session 很多”。LoCoMo 上没东西可忘，不代表 LongMemEval 上没东西可忘——恰恰相反，论文实测 44.4% 的失败就是漂移。

**修法**：保留这两个数字（它们是真的），但**删掉“遗忘机制不会被触发”这个推论**，换成更准确的说法：

> LoCoMo/LongMemEval 的**更新密度**低（多数问题只需 ≤2 session），不适合测**多步演进**；但它们仍能测单次状态漂移（StateMemBench 论文实测 LongMemEval oracle 上 44.4% 失败为 drift）。所以它们**可以作为机制有效性的一站，但不能作为长程遗忘的战场**——后者需要 Memora 或自建演进集。

这个说法既保留了原意（不能用 LoCoMo 证明长程遗忘），又不至于被一篇论文直接推翻。

### 8.3 “MemoBase 43.6 → 15.2、MemoryOS 51.8 → 25.1” —— 数字真实，但被误读

`memory_plugin.md:177` 引 Memora quarterly 的数字：

> 即使最强系统也只有 **20 多分/100**；memory agent 掉得最狠——MemoBase remembering 43.6 → **15.2**，MemoryOS 51.8 → **25.1**。

子代理核查结论：**这两个数字是真实的**，但文档对它们的解读有两处偏差：

1. **这组数字衡量的是“weekly → quarterly 的跨时限衰减”**，不是“季度内崩塌”。也就是说它是“短时限分数 vs 长时限分数”的对比，刻画的是**长程保持能力**，不是“系统在同一次评测里掉下去”。
2. **“最强系统也只有 20 多分”不准确**：Memora 的 Table 3 task-level FAMA 里，季度最高分是 **40.78** 和 **53.36**，不是“20 多分”。43.6→15.2 这一类是特定子系统/特定题型的数字。

此外这两个数字**不是 FAMA 总指标**，是 Table 3 的 task-level FAMA 分项——和 `project_plan.md:440` 要求的“报告官方 FAMA 及其 presence / absence 子项”不是同一层级。

**修法**：要么直接引用 Memora PDF 里的具体表号和列名，要么删掉具体数字、只保留定性结论。定性结论是**稳的**，两份论文都支持：

> memory agent 在长时限上掉得很厉害，多步推理几乎全场 0 分。

这句话可以放心用。**具体数字要么标表号，要么不写**——这是引用的基本纪律，尤其当这些数字要进 README 时。

### 8.4 xLSTM 的归因是“state tracking”，不是“两门独立”

`memory_plugin.md:55,90-96` 用 xLSTM 论文结论支撑“写入与淘汰必须分离”。

但该论文摘要的实际表述是：

> *"xLSTM delivers the strongest overall performance... Our results show that xLSTM enables more flexible and stable **memory correction** via its gating scheme... xLSTM's gains on complex tasks stem from robust **state tracking and accumulation**."*
> — [arXiv:2606.12364](https://arxiv.org/abs/2606.12364)

论文归因于**状态跟踪与记忆修正能力**，不是“两个门独立”。这个区别很关键：

- 论文支持的其实是 **“覆盖 + 修正 + 可回滚”** 这条线——**恰好是你的事件溯源 + undo**；
- 而不是 **“两个独立旋钮”** 那条线——那是 `gated_mem.md` 的“门控分离”叙事。

**建议**：把 LSTM 叙事从“门控分离”改成“**记忆修正（state correction）**”。两个好处：① 更贴合原文，不会被审稿人抓；② 和你真正的差异化（事件溯源 + undo）对齐，论证链从“类比”变成“同源”。

而且这样一来，`gated_mem.md` 的 ψ 连坐就**不再需要靠 LSTM 类比来撑**——它是独立的工程决策，§1.2 已经说明它证据偏弱，弱就弱，不必强行论证。

## 9. 关于“零经费开源”这个约束本身

这是整个方案的原点，值得单独说。`gated_mem.md:12` 说 v1.0 是“满分的工业级/学术级风控文档”，但在“零经费独立开源”约束下要做剪裁。

我理解这个约束的来源，但复核后认为**它被过度使用了**，理由有三：

1. **真正的成本不是钱，是注意力。** 按 §1.3 的测算，跑完 StateMemBench + 桥接实验的现金成本 <¥150。而按 `gated_mem.md` 的 7 天计划，如果 D7 才发现方案不成立，沉没的是 7 个工作日——这才是真正的“经费”。**先用钱换确定性，是零经费约束下的正解，不是违背它。**

2. **“不花钱”的隐性代价是结论不可信。** `gated_mem.md:158` 说要做“100% 确定性、零 API 费用”的检索层评测。这确实严谨，但它测得的东西（检索层指标）**恰好是 §5.2 引用的证据表明最不值钱的那一层**（时效操作只值 2.0pp）。用零成本的方法去测一个已知低价值的目标，是最差的组合。

3. **“零经费”被用来论证了一个不该由它论证的结论。** `gated_mem.md:21` 说因为没有 3-Judge 预算，所以用 50 组 Golden Fixtures 替代。但 `memory_plugin.md:213` 自己写过“50 个 case 不可信”。**这里缺的不是钱，是样本量**——而样本量可以通过“换用便宜的 judge + 减少配置组数”解决，不需要 50 个 case 这种妥协。

**建议**：把约束从“零经费”改成“**总预算 <¥600，且每一笔都必须在砍掉一个假设**”。这个表述保留了克制，但不至于让成本论证扭曲技术决策。

**关于 LSTM 叙事**：详见 §8.4。一句话——把叙事从“门控分离”改成“**记忆修正（state correction）**”，既贴合原文（"state tracking and accumulation"），又和你真正的差异化（事件溯源 + undo）对齐。而且这样改之后，ψ 连坐就不必再靠 LSTM 类比来撑——它是独立的工程决策，§1.2 已经说明它证据偏弱，弱就弱，不必强行论证。

## 一句话总结

> **你的机制不新（StateMem 的 Rechecker 就是连坐，MemStrata 就是槽位覆盖，两者都早你四个月）；你的核心卖点证据最弱（连坐 −12.5pp，时效操作只值 2.0pp）；你最贵的假设还没被检验（Table 6：纯 prompt 改写 56.7–75.0，碾压完整系统的 23.3–36.3）。**
>
> **但"可撤销 + 可解释 + 记住为什么变"这三件事，到现在仍然没有人在编码 agent 上做成产品——而它们恰好不受那些负面证据影响（撤销的价值不需要先证明存储有收益）。**
>
> **所以：先花半天、不到五十块，把"槽位覆盖有没有用"和"纯 prompt 是不是就够了"这两个问题问掉。答案会决定你是做插件、做 prompt 模板、还是做撤销工具。在拿到答案之前，一行 Day-1 代码都不该写。**
