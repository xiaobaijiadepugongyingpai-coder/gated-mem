# Gated-Mem 项目方案规划

> 版本：v1.0（基于当前构想与已核验事实的调整版）  
> 日期：2026-11-10  
> 决策：**可行但需调整，有条件 Go**  
> 项目性质：先验证状态记忆的核心价值，再决定是否投入自动遗忘、图谱可视化与跨宿主推广

---

## 1. 项目定位

### 1.1 一句话定义

面向单个开发者的长期编码项目，提供一个**本地、可解释、可回放、可撤销的 Agent 状态记忆工具**，减少过期架构决策和失效项目约束对后续回答的污染。

### 1.2 核心验证假设

在相同上下文 Token 预算下，显式维护当前状态、历史版本和覆盖关系，能够：

1. 降低过期事实被召回和采用的概率；
2. 不显著损害当前有效事实的召回；
3. 让每次记忆写入、注入、覆盖和人工干预均可解释、可撤销；
4. 在真实开发工作流中具有持续使用价值。

“LSTM 门控”仅作为写入、保留、输出三类策略分离的设计语言，不宣称实现了神经网络 LSTM，也不预设门控、幂律或 EMA 一定优于简单基线。

### 1.3 首要问题

长期编码项目中，数据库选型、测试规范、目录约束、技术决策等会随时间变化。普通向量检索可能同时返回新旧事实，却无法说明哪一个当前有效，从而导致旧决策继续影响新任务。

### 1.4 决策边界

- **可以启动**：本地状态记忆核心、Claude Code 单宿主适配、CLI 解释与回放、对照实验。
- **暂缓启动**：自动覆盖、自动 EMA 调参、Cursor 第二宿主、动态图谱、传播包装。
- **应停止的情况**：坚持仅按余弦相似度自动覆盖，或只追求演示效果而不进行同预算基线验证。

## 2. 目标用户与首发场景

### 2.1 目标用户

- 使用 Claude Code 的个体开发者；
- 同一项目会跨多个会话、数周持续开发；
- 已遇到或容易遇到历史决策污染当前上下文的问题；
- 接受本地存储和少量显式记忆管理操作。

### 2.2 首发记忆范围

| 类型 | 示例 | 默认保留策略 |
|---|---|---|
| 项目决策 | “主数据库从 MySQL 切换为 PostgreSQL” | 慢衰减；覆盖需明确关系 |
| 项目约束 | “所有测试使用 pytest” | 慢衰减；允许人工 Pin |
| 稳定偏好 | “回复使用中文” | 慢衰减；允许显式修改 |
| 临时观察 | “本次失败可能与缓存有关” | 快衰减；默认不进入长期核心状态 |
| 工具输出 | 一次构建日志、单次查询结果 | 默认不写入长期记忆 |

### 2.3 明确不做

首版不做：

- 通用个人助理记忆；
- 企业多租户、团队权限与共享记忆；
- 通用 GraphRAG、实体关系全量抽取；
- 基座模型训练、微调或 test-time training；
- 自动物理删除原始记忆；
- 对所有自然语言矛盾进行完全自动裁决；
- 将合成演示数据作为产品有效性证据；
- 以 Star 数、动画效果作为核心产品验收标准。

## 3. 总体架构

### 3.1 分层设计

```text
Claude Code
  ├── Hooks 适配器：确定性捕获、按需注入、宿主事件日志
  └── MCP Client
        ↓ stdio
Gated-Mem Core
  ├── Write Gate：是否写入、记忆类型、初始保留参数
  ├── State Manager：版本、覆盖候选、状态裁决、撤销
  ├── Retention：按类型衰减，不默认删除原文
  ├── Retrieve / Output Gate：候选检索、有效状态过滤、预算控制
  ├── Feedback：显式反馈与自报反馈，区分可信度
  ├── Explain / Replay：来源、原因、覆盖链、历史投影
  └── SQLite：记忆、版本、事件、边、反馈、向量索引

CLI：查询、解释、Pin / Kill / Undo、导出、诊断
Web：后续阶段只读时间线与覆盖链，验证后再考虑力导向图
```

### 3.2 宿主能力边界

- **MCP Core**：提供模型可调用的工具，不假定服务器能够看到最终回答。
- **Claude Code Hooks**：负责宿主生命周期中的确定性捕获与上下文注入，与 MCP 分开实现。
- **Cursor**：后续仅承诺其真实支持的 MCP 主动调用和手动反馈，不承诺与 Hooks 相同的自动化闭环。

## 4. 核心数据与状态设计

### 4.1 记忆结构

每条记忆至少包含：

```text
memory_id
project_id
content
memory_type
subject / entity
predicate / slot
scope
valid_from / valid_to
status = active | candidate_conflict | superseded | archived | killed
source_event_id
created_at / created_step
input_weight
retention_beta
half_life_steps 或 half_life_seconds
pinned
embedding_model_id / embedding_dim
```

首版可使用结构化字段加自由文本；无法可靠抽取 `subject/predicate/scope` 时，不得自动判定覆盖。

### 4.2 事件与投影

采用不可变事件日志：

```text
memory_events(
  event_id,
  project_id,
  step,
  event_type,
  payload_json,
  created_at
)
```

事件类型至少包括：

```text
MEMORY_CREATED
CONFLICT_CANDIDATE_CREATED
MEMORY_SUPERSEDED
MEMORY_RESTORED
MEMORY_PINNED
MEMORY_KILLED
MEMORY_UNDONE
RECALL_DELIVERED
FEEDBACK_SELF_REPORTED
FEEDBACK_USER_VERIFIED
```

当前状态是事件日志的投影。历史回放必须基于事件重建，不能只保存当前状态和聚合计数。

### 4.3 关系类型

```text
SUPERSEDES       经裁决的新状态覆盖旧状态
DUPLICATES       内容去重，不等于状态覆盖
REFINES          对原记忆补充或细化
CONTRADICTS      存在矛盾，但尚未决定当前有效值
CO_CITED         仅由有效反馈产生，首版后置
BELONGS_TO       项目或命名空间归属
```

每条关系保存：来源、目标、裁决方式、证据、置信度、创建事件和撤销事件。

## 5. 关键机制设计

### 5.1 写入与冲突处理

```text
新记忆
  → 判断是否值得长期保存
  → 向量检索只用于寻找候选
  → 比较 subject / predicate / scope / temporal 信息
  → 关系分类
  → 证据充分才改变状态
  → 否则保持原状态并进入待确认列表
```

关系分类：

```text
independent | refines | duplicates | contradicts | supersedes
```

禁止：

- 将固定余弦区间直接映射为 `SUPERSEDES`；
- 将高相似度一律视为重复；
- 因 namespace 相同就覆盖其中的旧记忆；
- 在无证据时根据“更新”自动判定“更正确”。

自动覆盖开放前，必须建立人工标注集并达到第 9 节的精度门槛。未达门槛时永久保留“仅建议、人工确认”的降级路径。

### 5.2 衰减与保留

统一采用可比较的保留函数：

\[
R(\Delta)=(1+\Delta/t_0)^{-\beta},\qquad \Delta\geq0
\]

\[
H=t_0(2^{1/\beta}-1)
\]

约定：

- `β` 按记忆类型固定；
- `H` 为动态半衰期；
- 时间单位明确，真实时间与逻辑 step 分开；
- 衰减仅影响排序和注入，不自动物理删除；
- `Pin` 禁止自动衰减；
- `Kill` 不被普通检索或普通反馈复活；
- 幂律与指数曲线通过实验比较，不预设幂律必然胜出；
- 保留率 `R` 不直接等同于 LSTM 的 `f_t`，输出门单独计算。

必须覆盖的单元测试：

```text
R(0) = 1
R(H) = 0.5
R(2H) = 0.25
β → 0 时 R → 1
时间单位换算一致
Pin 不衰减
Kill 不被普通反馈复活
```

### 5.3 检索与输出门

检索流程：

```text
查询
  → 向量 / BM25 候选
  → 过滤 killed、已失效且不应注入的历史状态
  → 结合当前有效性、语义相关性、保留率排序
  → 在固定 Token 预算内选择
  → 返回 recall_event_id、memory_ids、理由和版本信息
```

输出必须能回答：

- 为什么返回这条记忆；
- 它是当前状态还是历史状态；
- 谁覆盖了旧状态；
- 本次过滤了哪些高相似候选及原因；
- 使用了多少注入 Token。

首版对照基线至少包含：

1. 无记忆；
2. 向量 + 新近度，无状态覆盖和遗忘；
3. 同 Token 预算的完整或扩展上下文（适用时）；
4. 本方案。

### 5.4 反馈生命周期

召回时记录：

```text
recall_event_id
project_id
delivered_memory_ids
delivered_at
status = delivered | pending | expired | self_reported | user_verified
```

反馈规则：

- 未回传不等于未使用，不作负标签；
- 自报 `cited_ids` 必须属于对应召回批次；
- 自报反馈只标记为 `self_reported`；
- 用户 Pin、Kill、纠错和撤销属于高可信反馈；
- 不把整批记忆自动归因于任务成功；
- 首版不根据未回传自动衰减；
- 自动 EMA 仅在积累足够可信反馈后单独立项验证。

### 5.5 可撤销与人工控制

CLI 首版提供：

```text
gated-mem list
gated-mem show <memory_id>
gated-mem explain <recall_event_id>
gated-mem conflicts
gated-mem pin <memory_id>
gated-mem kill <memory_id>
gated-mem undo <event_id>
gated-mem replay --step <step>
gated-mem doctor
```

所有覆盖、Kill、Boost 和人工修改均生成新事件，不原地抹除历史。

## 6. 工程实现方案

### 6.1 技术栈

- Python；
- SQLite，启用外键、WAL、`busy_timeout` 和短事务；
- MCP stdio Server；
- Claude Code Hooks 适配器；
- 本地多语言 embedding，固定模型 ID、版本、维度和许可证；
- `sqlite-vec` 可选；小库提供 NumPy 暴力余弦回退；
- CLI 首版，Web UI 后置。

### 6.2 工程约束

- 固定 Python、MCP、embedding、向量扩展等依赖版本并生成 lockfile；
- 不依赖未锁定的 MCP 旧版 API；
- stdio 日志只写 stderr；
- 数据库按 `project_id` 隔离，禁止不同项目串库；
- 记忆、向量、候选关系在同一逻辑事务中提交；
- 写操作幂等，必要时采用单写者或写入队列；
- embedding 更换后整库重建向量，不混用不同维度或模型；
- 首次模型下载、缓存目录、校验和、断网启动均需验证；
- 本地 UI 若提供写操作，必须增加随机端口、token、Origin 校验、输入转义和非通配 CORS；首版优先只读；
- UI 的 JS/CSS 若承诺完全本地运行，不得依赖 CDN；
- 演示种子仅用于开发，不参与效果验收。

### 6.3 建议模块

```text
gated-mem/
├── pyproject.toml
├── src/gated_mem/
│   ├── schema.py          # 数据模型与状态枚举
│   ├── events.py          # 事件追加、投影、撤销与回放
│   ├── gates.py           # 保留函数、输出排序，不包含伪 LSTM 宣称
│   ├── conflicts.py       # 候选生成、关系分类、人工裁决
│   ├── retrieval.py       # 候选检索、有效状态过滤、预算控制
│   ├── feedback.py        # 召回事件和反馈生命周期
│   ├── storage.py         # SQLite、迁移、事务、索引
│   ├── embeddings.py      # 模型固定、缓存与回退
│   ├── server.py          # MCP 工具
│   ├── cli.py             # 管理与解释命令
│   └── adapters/
│       └── claude_code.py # Hooks 安装与宿主事件适配
├── tests/
├── fixtures/
└── scripts/
```

## 7. 分阶段交付计划

> 工期为单人工程估算，不含不可控的数据集适配和外部审核等待。5 天仅用于技术 Spike，不作为有效产品交付承诺。

### 阶段 A：5 天技术 Spike

| 时间 | 工作内容 | 验收产出 |
|---|---|---|
| Day 1 | 记忆模型、事件日志、状态机、保留公式与单测 | 可创建、覆盖、恢复、Pin、Kill、Undo、Replay |
| Day 2 | SQLite、向量/BM25 候选、输出过滤、冲突候选 | 新旧事实可共存；相似度不会直接覆盖 |
| Day 3 | MCP 工具与 Claude Code Hooks 最小闭环 | 真实客户端 list/call、捕获、召回、重启恢复 |
| Day 4 | CLI 解释、反馈状态、项目隔离、事务与迁移 | 每次注入可解释；未反馈不受惩罚；两项目不串库 |
| Day 5 | 黄金 fixture、故障注入、冒烟与离线打包 | 可重复演示；形成真实 Token、延迟和失败清单 |

**阶段出口**：闭环可走通且状态操作可恢复，才进入对照实验。若只能展示假数据动画，不视为通过。

### 阶段 B：核心实验与 MVP（约 2–3 周）

1. 建立开发集、验证集、冻结测试集，禁止在测试集调参；
2. 完成无状态基线与本方案的同 Token 预算比较；
3. 先验证显式状态覆盖，再验证衰减是否有增量收益；
4. 构造至少 200 对冲突/非冲突人工标注样本；
5. 对独立参数与单分数、幂律与指数、反馈更新与固定参数逐项消融；
6. 记录所有误覆盖、误过滤、旧事实回答和无反馈情况；
7. 只在核心机制通过后补只读时间线与覆盖链。

### 阶段 C：真实用户试点（约 1–2 周，可与阶段 B 后半段并行）

1. 访谈至少 10 名目标开发者；
2. 在至少 5 个真实项目中安装；
3. 收集至少 30 个非合成工作会话；
4. 观察安装成功率、解释使用率、纠错率、第二周留存；
5. 收集真实过期事实案例，而非只收集主观满意度；
6. 根据证据决定继续状态记忆、转为诊断工具，或停止项目。

### 阶段 D：通过门槛后的扩展

按优先级逐项开放：

1. 只读记忆时间线与覆盖链；
2. 本地只读 Graph UI；
3. 经精度验证的有限自动覆盖；
4. 经对照验证的 EMA；
5. Cursor 适配；
6. 静态演示、GIF 和开源传播；
7. 多用户、多 Agent 等另立项目评估。

## 8. 实验设计

### 8.1 数据集定位

| 数据集 | 已核验规模 | 用途 | 注意事项 |
|---|---:|---|---|
| StateMemBench | 234 场景、322 graded probes | 当前状态与过期状态区分 | 使用其 closed-pool 指标，不称为 FAMA |
| Memora weekly | 150 题 | 快速流程与遗忘指标验证 | 使用 FAMA，注意部分题无 forgetting 子项 |
| Memora quarterly | 300 题 | 长周期更新验证 | 数据与真实编码场景存在领域差异 |
| 真实编码项目集 | 逐步建立 | 验证产品价值 | 不能由通用对话基准替代 |

参考实现与论文：

- StateMemBench：<https://arxiv.org/abs/2608.19652>
- Memora / FAMA：<https://aclanthology.org/2026.findings-acl.1337/>
- Memora 数据与代码：<https://github.com/geniesinc/Memora>
- FadeMem：<https://arxiv.org/abs/2601.18642>
- Weighted Memory Tree：<https://arxiv.org/abs/2608.20631>

### 8.2 实验公平性

- 固定生成模型、judge 模型、版本和解码参数；
- 对比系统使用相同回答 backend；
- 同 Token 预算，不以不同预算制造优势；
- 开发、验证、测试数据隔离；
- 每项重要结论至少 3 次重复，报告 bootstrap 95% CI；
- 同时报告平均值、长尾失败、误覆盖和 false forget；
- 记录实际 ingest、检索、回答、judge 的 Token 与费用；
- StateMemBench 报告 current-state accuracy、superseded/drift 等指标；
- Memora 报告官方 FAMA 及其 presence / absence 子项；
- 合成 fixture 用于调试，不用于对外效果宣称。

### 8.3 核心消融顺序

1. **状态表示**：向量 + 新近度 vs 显式覆盖状态；
2. **遗忘净收益**：无衰减 vs 有衰减；
3. **曲线形状**：固定其他条件后比较幂律与指数；
4. **参数拆分**：独立写入/保留参数 vs 单一 importance；
5. **反馈更新**：固定参数 vs 经验证反馈驱动的更新。

若前一项没有收益，不继续堆叠后一项复杂机制。

## 9. Go / No-Go 验收门槛

以下为项目预设验收目标，不是现有实验结果。

### 9.1 核心正确性门槛

- 所有状态修改可追踪、可回放、可撤销；
- Pin、Kill、Undo 的自动化测试全部通过；
- 不同项目数据隔离测试全部通过；
- 未回传反馈不会触发负向衰减；
- 每次注入的来源、时间、原因和版本解释覆盖率为 100%；
- 冲突候选不会仅凭余弦相似度改变状态。

### 9.2 核心效果门槛

与同 Token 预算的“向量 + 新近度、无遗忘”基线比较：

- 当前状态准确率或适用的 FAMA 相对提升目标 ≥10%，且 bootstrap 95% CI 下界 >0；
- 过期召回率相对下降目标 ≥30%；
- Token/query 不高于基线；
- 若只减少 Token、效果不升，判核心遗忘机制不通过；
- 若独立门控不优于简单单分数基线，撤销“门控分离是核心壁垒”的主张；
- 若显式覆盖状态也不优于简单基线，停止自动遗忘路线，评估转为纯状态诊断工具。

### 9.3 自动覆盖开放门槛

- 至少 200 对人工标注的冲突/非冲突样本，包含兼容、并列、不同主体、不同 scope、精化与真正覆盖；
- 自动覆盖精度目标 ≥98%；
- 受保护记忆及指定关键当前事实的误覆盖数为 0；
- 所有误操作 100% 可恢复；
- 达不到门槛则保持“仅建议、不自动覆盖”。

### 9.4 工程门槛

- 安装无需 Docker；
- 目标用户安装成功率 ≥80%；
- 中位安装时间 ≤10 分钟；
- 1 万条本地记忆时，检索 P95 <500ms，不含宿主 LLM；
- 重启后状态可恢复；
- 离线运行路径不依赖 CDN；
- embedding 模型下载失败和扩展加载失败均有明确降级或错误提示。

### 9.5 产品门槛

- 至少 10 名目标用户访谈；
- 至少 5 个真实项目安装；
- 至少 30 个非合成工作会话；
- 至少 3 名用户第二周仍主动使用；
- 注入记忆“有用”的人工评价目标 ≥70%；
- 过期事实问题较原工作流有明确下降；
- 未达到留存门槛，不继续投入动态图谱和传播功能。

## 10. 成本与宣传口径

### 10.1 成本口径

可宣称：

> 核心引擎无需独立云 API，可复用用户已有宿主模型；本地存储与检索可离线运行。

不可直接宣称：

- 整个项目及正式实验成本为 ¥0；
- 宿主模型没有推理成本；
- 本地 embedding 永远无需下载；
- 多 judge 实验无需模型或算力预算；
- 本地运行等于零资源消耗。

实验预算单独立项，先通过小规模 smoke run 测量真实 Token、缓存命中、运行时间与失败重试，再估算全量费用。

### 10.2 效果口径

- `excluded_stale_candidates`：被过滤的过期候选数，可直接统计；
- `injected_tokens`：实际注入 Token，可直接统计；
- “节省 Token”：必须与同查询、同任务基线比较后才能报告；
- “避免冲突”：只有观测到过期回答或用户纠正减少后才能报告；
- 不得把“潜在风险数量”写成“已经避免的事故数量”；
- 不使用“转化率下降 90%”“Star 翻 3 倍”“100 到 5000 Star”等无依据数字指导决策。

## 11. 主要风险与降级路径

| 风险 | 应对 | 降级路径 |
|---|---|---|
| 相似度误覆盖 | 仅生成候选，结构化裁决，保留历史 | 永久人工确认 |
| 宿主反馈不可靠 | 区分 delivered / self_reported / verified | 仅使用显式用户反馈 |
| 衰减误伤长期知识 | 衰减只影响注入，Pin 保护，可恢复 | 关闭自动衰减 |
| MCP 无法自动捕获 | Claude Code Hooks 单独适配 | 显式 add/search，不承诺自动闭环 |
| 本地模型或扩展安装失败 | 固定版本、预热、诊断、暴力检索回退 | BM25 / NumPy 小规模模式 |
| 基准与编码领域不一致 | 增加真实项目试点 | 只保留已验证场景 |
| 核心机制无增量收益 | 与简单基线同预算比较 | 转为解释/诊断工具或停止 |
| 用户不愿持续使用 | 观察第二周留存和真实纠错 | 停止图谱与推广投入 |

## 12. 最终执行原则

1. **先状态正确，再谈遗忘。** 新旧事实的关系不能被向量相似度替代。
2. **先可逆，再谈自动。** 所有自动化都必须保留人工控制和恢复路径。
3. **先简单基线，再谈创新。** 不能胜过向量 + 新近度，就不增加复杂门控。
4. **先真实闭环，再谈跨宿主。** MCP 接入不等于工作流集成。
5. **先同预算效果，再谈 Token 节省。** 全删可以省 100%，但没有产品价值。
6. **先真实留存，再谈图谱传播。** 图谱是解释和展示层，不是核心壁垒。
7. **每个阶段设置停止条件。** 证伪核心假设时及时缩减或终止，而非继续堆功能。

**项目建议：按上述范围有条件启动；首个里程碑不是“做出动态图谱”，而是“在真实宿主中可回放、可解释、可撤销地维护当前状态，并用同预算实验证明减少过期召回”。**
